一、对象的诞生：new 一行代码背后发生了什么？

1.1 类加载检查

  • JVM 遇到 new 指令，先去常量池定位类的符号引用
  • 检查类是否已完成加载 → 链接 → 初始化三步
  • 未加载则触发类加载过程（双亲委派模型简述）

1.2 内存分配

  • 分配方式：指针碰撞（Bump the Pointer，Serial/ParNew 等带压缩的收集器）vs 空闲列表（Free List，CMS 等非压缩收集器）
  • TLAB（Thread Local Allocation Buffer）：线程私有的分配缓冲区，避免 CAS 竞争
  • 分配失败：TLAB 不够 → 堆上 CAS 分配 → 都不行 → 触发 Minor GC → 还不行 → Full GC → 再不行 → OOM

1.3 对象初始化

  • 零值初始化：分配到的内存空间先全部归零（保证实例字段默认值）
  • 对象头设置：Mark Word（hashCode、GC 分代年龄、锁状态）+ Klass Pointer（类型元数据指针）
  • <init> 方法：执行构造器代码，按顺序完成实例变量赋值 + 构造代码块

二、对象的内存布局：24 字节里装了什么？

2.1 Mark Word（标记字）

  • 记录对象自身的运行时数据：hashCode、GC 分代年龄、锁状态标志、线程持有的锁、偏向线程 ID
  • Mark Word 的动态复用机制——同一块空间在不同锁状态下存储不同含义的数据
  • 偏向锁 → 轻量级锁 → 重量级锁 → GC 标记的 Mark Word 变化过程

2.2 Klass Pointer（类型指针）

  • 指向方法区中 Klass 元数据的指针
  • 压缩指针（-XX:+UseCompressedOops）：64 位下 8 字节 → 4 字节

2.3 实例数据与对齐填充

  • 实例数据排列规则：父类字段在前、同宽度字段尽量排在一起
  • 对齐填充（Padding）：HotSpot 要求对象大小必须是 8 字节的整数倍
  • 一个 new Object() 到底占多少字节？32 位 vs 64 位 vs 64位+压缩指针

  • 句柄访问：栈上 reference → 句柄池（含对象指针 + 类型指针）→ 实例数据 / 类型数据。好处：GC 移动对象时只改句柄池，reference 本身不变
  • 直接指针：栈上 reference → 对象（含类型指针）→ 类型数据。好处：少一次间接寻址，更快

3.2 HotSpot 的选择

  • HotSpot 采用直接指针访问（少一次间接寻址，性能更好）
  • 代价：GC 移动对象时必须更新所有指向它的 reference

四、对象的生存：堆里的日子

4.1 引用与逃逸

  • 对象被引用传递：局部变量 → 方法参数 → 成员字段 → static 字段
  • 逃逸分析回顾：不逃逸则标量替换 / 锁消除（详见上篇）
  • 引用强度决定了 GC 对它的态度（见 5.4）

4.2 分代晋升之路

  • Eden 区出生：绝大多数对象在这里分配
  • 第一次 Minor GC：存活对象 → Survivor0（From 区），分代年龄 +1
  • 反复横跳：每次 Minor GC，在 S0 / S1 之间来回拷贝，年龄 +1
  • 晋升老年代：年龄达到 -XX:MaxTenuringThreshold（默认 15）→ 或者 Survivor 空间不够 → 空间担保分配直接进老年代
  • 大对象直接进老年代：超过 -XX:PretenureSizeThreshold 的对象

4.3 对象在堆里的三种"状态"

  • 强可达（Strongly Reachable）：至少有一条 GC Roots 强引用链
  • 软可达/弱可达/虚可达：JDK 引用类型决定（见 5.4）
  • 不可达：等待被清除的「垃圾」

五、对象的死亡：GC 怎么判定谁能回收？

5.1 引用计数法（Java 没选这条路）

  • 原理：每个对象维护被引用次数，归零即回收
  • 致命缺陷：循环引用导致永远无法回收（A ↔ B，但外部已不可达）
  • 为什么不用：Java 对象间双向引用太常见

5.2 可达性分析（Reachability Analysis）——Java 的方案

  • GC Roots 集合：哪些引用可以当作"绝对存活的根"？
    • 虚拟机栈中引用的对象（局部变量）
    • 方法区中 static 字段引用的对象
    • 方法区中常量池引用的对象（String.intern()）
    • JNI 引用的对象
    • 虚拟机内部引用（Class 对象、常驻异常对象、ClassLoader）
    • 所有被 synchronized 持有的对象
  • 从 GC Roots 向下搜索引用链（Reference Chain），链上的对象存活，不在链上的……也不是立刻死

5.3 对象的"两次标记"与自救

  • 第一次标记：不可达 → 进入筛选队列
  • finalize() 自救：重写 finalize() 并在方法内重新建立 GC Roots 引用链 → 逃脱回收（仅一次机会，finalize 只会被 JVM 调用一次）
  • 第二次标记：队列中的对象如果 finalize 也没自救 → 真正回收
  • finalize() 已被 JDK 9 标记为 @Deprecated，JDK 18+ 正式废弃——替代方案：Cleaner + PhantomReference

5.4 四种引用强度（核心面试题）

引用类型 回收时机 典型用途
强引用 Strong 永不回收（除非 GC Roots 不可达） Object o = new Object()
软引用 Soft 内存不足（OOM 前）才回收 缓存、图片缓存
弱引用 Weak 下次 GC 立即回收 WeakHashMap、ThreadLocal
虚引用 Phantom 任何时候，仅作为回收通知 Cleaner 机制、NIO 直接内存回收

6.2 分代收集理论（Generational Collection）

  • 弱分代假说：绝大多数对象朝生夕死
  • 强分代假说：熬过越多次 GC 的对象越难死
  • 跨代引用假说：跨代引用相对同代引用只是极少数 → Remembered Set 解决
  • 新生代（Young Gen）：Minor GC，标记-复制，高频快速
  • 老年代（Old Gen）：Major/Full GC，标记-清除/整理，低频慢速

6.3 HotSpot 经典收集器速览

收集器 位置 算法 特点
Serial 新生代 标记-复制 单线程，Client 模式默认
ParNew 新生代 标记-复制 Serial 的多线程版
Parallel Scavenge 新生代 标记-复制 吞吐量优先
Serial Old 老年代 标记-整理 Serial 的老年代版
Parallel Old 老年代 标记-整理 Parallel Scavenge 的老年代配对
CMS 老年代 标记-清除 低停顿，并发收集，已废弃(JDK14)
G1 全堆 混合 Mixed 区域化 Region，可预测停顿
ZGC / Shenandoah 全堆 染色指针 超低延迟（<1ms），TB 级堆

6.4 一个对象的"临终"时间线 

new 分配 → Eden → Minor GC → Survivor 往返 → 晋升 Old → Major GC → 标记 → 清除/整理 → 内存归还
