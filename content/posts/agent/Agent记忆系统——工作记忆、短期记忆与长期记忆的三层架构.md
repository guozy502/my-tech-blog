# Agent 记忆系统——让 Agent 记住你昨天说了什么

> 跟 ChatGPT 聊天最烦的事：翻到昨天的对话，它完全不记得你是谁。Agent 也一样——没有记忆系统的 Agent 每次对话都从零开始。本文从工作记忆、短期记忆、长期记忆三层模型出发，拆解上下文窗口管理、检索策略、以及 MemGPT 等前沿方案的核心设计。

---

## 一、为什么记忆是 Agent 的核心瓶颈

### 1.1 上下文窗口 ≠ 记忆

所有 LLM 都有一个上下文窗口（GPT-4 128K、Claude 200K、Gemini 2M token）。表面看，"我把历史全塞进去不就行了？"

实际上：
- **成本问题**：128K token 的上下文，每次 API 调用都要处理全部内容。按 GPT-4 的 128K 输入定价，一轮对话轻松吃掉 $0.3+
- **注意力稀释**：LLM 的注意力机制在长上下文中有"中间丢失"现象（Lost-in-the-Middle）——放在中间的信息被检索到的概率显著低于开头和结尾
- **延迟**：prefill 阶段的时间和上下文长度呈二次方关系

所以"好记性"不是把东西全塞进去，而是**在正确的时间把正确的信息放到上下文中**。

### 1.2 三层记忆模型

受认知心理学启发，Agent 记忆系统也分三层：

```
┌──────────────────────────────────────────────┐
│              Agent 记忆系统                    │
│                                              │
│  ┌─────────────┐                             │
│  │ 工作记忆     │  ← 当前对话的 token 窗口     │
│  │ Working Mem │     容量: ~100K tokens       │
│  │             │     生命周期: 一次对话        │
│  └──────┬──────┘                             │
│         │ 对话结束后，压缩/摘要                │
│         ▼                                    │
│  ┌─────────────┐                             │
│  │ 短期记忆     │  ← 近期对话摘要 + 关键信息    │
│  │ Short-term  │     容量: ~最近 10-20 次对话  │
│  │             │     生命周期: 天~周           │
│  └──────┬──────┘                             │
│         │ 重要的信息持久化                     │
│         ▼                                    │
│  ┌─────────────┐                             │
│  │ 长期记忆     │  ← 向量数据库 / 知识图谱     │
│  │ Long-term   │     容量: 几乎无限            │
│  │             │     生命周期: 永久             │
│  └─────────────┘                             │
└──────────────────────────────────────────────┘
```

## 二、工作记忆 —— 上下文窗口内的博弈

### 2.1 Token 预算管理

把上下文窗口看作一个有上限的"内存预算"，每次系统 prompt、工具定义、对话历史、工具返回结果都在消耗这个预算。你需要精打细算。

```
典型 128K 窗口的预算分配:

系统 Prompt:        ~2K tokens   (角色设定、规则、工具定义)
对话历史:           ~20K tokens  (最近 N 轮对话)
工具调用+结果:       ~30K tokens  (搜索结果、API 返回)
检索到的长期记忆:    ~5K tokens   (向量库查到的相关记忆)
预留缓冲区:          ~71K tokens  (给 LLM 输出的空间)
```

### 2.2 滑动窗口 vs 摘要压缩

当对话越来越长，预算吃紧，你要么"丢掉旧的"，要么"压缩旧的"。

**滑动窗口 (Sliding Window)**：

```
保留最近 K 轮对话，更早的直接丢弃

优点: 简单，实现成本低
缺点: 丢失重要上下文（比如用户在第 2 轮说过"我对花生过敏"，
      到第 20 轮已经被丢弃，Agent 可能推荐含花生的菜品）
```

**摘要压缩 (Summarization)**：

```
每 N 轮对话后，调用 LLM 生成摘要:
"用户喜欢川菜，对花生严重过敏，目标是找一个适合 4 人聚餐的餐厅。
已排除: A餐厅(无包间)、B餐厅(评分低)。当前在看 C 餐厅的菜单。"

历史 = 摘要 + 最近 K 轮原始对话
```

摘要压缩的进阶技巧：
- **分层摘要**：不只是从原始对话生成摘要，而是从"旧摘要 + 新对话"生成更新摘要，形成递归压缩
- **多维度摘要**：分别摘要"用户偏好"、"任务进度"、"关键决策"、"待解决问题"，而非一段混合文本
- **保留关键实体**：人名、日期、编号、确认的选项——这些不参与压缩，原样保留

### 2.3 注意力窗口的物理位置

LLM 的注意力机制对上下文不同位置的关注度是不均匀的：

```
注意力强度:
  高 ████████████ (开头: primacy bias)
     ████
     ██          (中间: lost-in-the-middle)
     ████
  高 ████████████ (结尾: recency bias)
```

这意味着：
- **最重要的指令放开头或结尾**
- **检索到的长期记忆放开头**（远离开头太远会被忽略）
- **最新工具调用结果放结尾**（利用近因效应）
- 如果你需要 LLM 关注中间某段信息，用特殊标记包裹：`<!-- IMPORTANT: ... -->`

## 三、短期记忆 —— 跨对话的上下文延续

### 3.1 存什么

不是每轮对话都值得存档。值得存的：

| 应存储 | 不应存储 |
|--------|---------|
| 用户偏好（"我喜欢简洁的回答"） | 寒暄内容（"你好"、"谢谢"） |
| 用户事实信息（"我在字节工作"） | 中间推理过程 |
| 任务进度（"上次写到第三章"） | 已解决的临时问题 |
| 用户反馈（"上次给你的方案太啰嗦"） | 重复的工具调用 |
| 重要决策及原因 | LLM 的自我说明 |

### 3.2 怎么存

**方案 A：对话摘要**

每次对话结束后，调用 LLM 提取摘要并存入短期记忆库：

```
摘要格式:
{
  "session_id": "sess_20260729_001",
  "timestamp": "2026-07-29T14:30:00",
  "summary": "用户要求分析竞品定价，完成了数据收集但尚未生成报告",
  "user_preferences": {"回答风格": "简洁", "格式偏好": "Markdown"},
  "key_decisions": ["使用公共数据源而非付费API", "只关注前3名竞品"],
  "pending_tasks": ["生成竞品分析报告", "制作对比表格"]
}
```

**方案 B：关键事件提取**

不存摘要，而是提取离散的、可索引的"记忆条目"：

```
条目 1: 用户对花生严重过敏（来源：2026-07-15 对话）
条目 2: 用户使用 macOS，偏好 zsh 终端（来源：2026-07-20 对话）
条目 3: 用户正在写一本关于 Agent 的博客系列（来源：2026-07-29 对话）
```

每条记忆可以独立检索，更适合向量化的记忆系统。

### 3.3 短期记忆的生命周期

不是所有记忆都永不过期。引入时间衰减：

```
记忆权重 = 初始重要性 × e^(-λ × 天数) × 最近访问加成

- 用户过敏信息: 重要性=1.0, 几乎不衰减 (λ→0)
- 某次具体的搜索结果: 重要性=0.3, 7天后权重趋于0
- 用户的临时偏好："今天想吃中餐": 重要性=0.5, 1天后权重趋零
```

这个衰减函数不是自动算的——你需要一个字段标注每段记忆的重要性级别，或者用 LLM 在存储时打出权重。

## 四、长期记忆 —— 检索 + 存储

### 4.1 记忆的向量化

长期记忆需要"按内容检索"能力，而不是按时间查找。流程：

```
1. 写入: 重要事件 → LLM 摘要 → embedding 模型向量化 → 存入向量数据库
2. 读取: 用户新消息 → embedding → 在向量库中 top-K 相似检索 → 注入上下文
```

**embedding 模型选择**：

| 模型 | 维度 | 特点 |
|------|------|------|
| text-embedding-3-small | 512/1536 | OpenAI，性价比高 |
| text-embedding-3-large | 256/1024/3072 | OpenAI，质量最好 |
| bge-large-zh-v1.5 | 1024 | 中文场景最优 |
| jina-embeddings-v3 | 1024 | 支持任务特定 LoRA |

### 4.2 混合检索 —— 只用向量不够

向量检索擅长语义相似度，但对"精确匹配"很弱：

```
用户: "我上次提到的那个 project-x 怎么样了？"

向量检索: 找到一堆跟 project 和 x 相关的记忆，但可能没找对具体的那条
关键词检索: 精确匹配 "project-x"，直接命中
```

**混合检索 (Hybrid Search)** 是业界共识：

```
最终分数 = α × 语义相似度 + (1-α) × BM25 关键词匹配分
```

在原始检索结果上再做 **reranker** (Cross-Encoder) 精排：将每条结果和查询一起喂给 reranker 模型，计算真正的相关性分数——比向量相似度准确得多，只是成本更高。

### 4.3 检索时机 —— 什么时候该翻记忆

不需要每句话都去查记忆库。触发检索的时机：

- **开场白**（对话开始的第一条消息）
- **显式信号**："上次我们聊的那个……"、"之前你说过……"
- **信息缺口**：当前对话中缺少关键信息（用户偏好、历史决策等），由 LLM 判断是否信息不足，主动触发检索

不是所有检索到的记忆都直接注入——先让 LLM 判断相关性，只有通过检查的才放入上下文。这是"取出来→筛选→注入"的三步流程。

## 五、MemGPT 的设计思路——像 OS 一样管内存

MemGPT 是目前 Agent 记忆领域最具原创性的工作之一，它的核心洞察是：**LLM 的上下文窗口就像 OS 的物理内存，我们需要"虚拟内存"**。

### 5.1 OS 类比

| OS 概念 | MemGPT 对应 |
|---------|------------|
| 物理内存 (RAM) | LLM 上下文窗口 (token 容量) |
| 虚拟内存 | 对话历史 + 向量存储 + 归档存储 |
| 页 (Page) | 一条消息 / 一段记忆 |
| 缺页中断 (Page Fault) | 信息不在上下文中，从外部存储加载 |
| 页置换 (Page Eviction) | 上下文满了，把旧内容换出到外部存储 |
| 内存管理单元 (MMU) | MemGPT 的 Memory Manager |

### 5.2 两级存储 + 自主管理

MemGPT 给 LLM 一个特殊的"记忆编辑"工具：

```
Agent 可调用的记忆工具:
- conversation_search(query): 搜索对话历史
- archival_memory_search(query): 搜索归档记忆（长期）
- archival_memory_insert(content): 写入归档记忆
- core_memory_replace(old, new): 替换核心记忆（用户画像等）
```

**核心创新的自主记忆管理**：LLM 自主决定什么时候存、什么时候查、什么时候替换。不是外部代码强制 flush，而是 LLM 通过 function calling 自己调用记忆工具。

例如，LLM 发现自己上下文快满了：

```
Thought: 当前上下文窗口剩余不足 20%。我需要把前 30 轮对话
         压缩为摘要并存入归档，释放空间继续当前任务。

Action: archival_memory_insert
Arguments: {"content": "对话第 1-30 轮摘要：用户要求设计餐厅推荐系统,
           讨论了数据源、排序算法和 UI 布局。关键决策：..."}
```

这个设计让记忆管理从"框架预定义策略"变成了"LLM 根据实际情况自主决策"，更灵活也更智能。

### 5.3 Letta 的工程化

MemGPT 的学术团队后来成立了 Letta，把想法工程化为可部署的服务：
- 记忆状态与 Agent 逻辑解耦，Agent 实例可以无状态 + 记忆服务持久化
- 支持多 Agent 共享记忆空间
- 提供记忆的版本管理和回滚

虽然 Letta 本身还很新，其设计思路正在被 LangChain、LlamaIndex 等框架吸收。

## 六、记忆系统的工程权衡

| 方案 | 实现难度 | 检索质量 | 成本 | 适用场景 |
|------|---------|---------|------|---------|
| 仅滑动窗口 | 极低 | - | 低 | PoC、一次性任务 |
| 滑动窗口 + 摘要 | 低 | 中 | 低 | 客服 Agent |
| 向量记忆 + 混合检索 | 中 | 高 | 中 | 个人助手、知识型 Agent |
| 向量记忆 + Reranker | 中高 | 极高 | 中高 | 需要高精度检索的产品 |
| MemGPT 式自主管理 | 高 | 高 | 高 | 长时间运行的自主 Agent |
| 知识图谱 + 向量 | 高 | 极高 | 高 | 多实体关系推理场景 |

### 6.1 记忆消解的问题

长期记忆有个棘手问题：**当两条记忆矛盾时怎么办？**

```
记忆 A (2026-07-01): 用户偏好简洁回答
记忆 B (2026-07-20): 用户要求"多给细节"
```

两条都检索到了，该信哪个？

方法：
- **时间加权**：越新的记忆权重越高（但有些偏好是长期稳定的，时间加权反而错）
- **信任度字段**：每条记忆附加一个 `confidence` 分数，由生成记忆时的 LLM 评估置信度
- **冲突检测 + 让用户裁决**：检索到冲突记忆时，直接在对话中问"我注意到你之前的偏好是 X，但最近问了 Y，我应该按哪个来？"

### 6.2 记忆的遗忘

人类不是记住了所有事，Agent 也应该是：
- **主动清理**：访问频次低、时间久远的记忆定期删除或降级到归档
- **覆盖更新**：同类信息只保留最新的一条（用户地址、手机号）
- **重要性判断**：让 LLM 在存储时打分，高分数的不遗忘，低分的自然淘汰

---

记忆系统的本质不是"存得越多越好"，而是**在正确的时间让正确的信息被 LLM 看到**。下一篇将深入 RAG——让 Agent 能利用外部知识的完整技术链路。
