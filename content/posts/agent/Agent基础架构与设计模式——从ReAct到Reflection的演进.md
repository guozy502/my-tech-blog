# Agent 基础架构与设计模式——从 ReAct 到 Reflection 的演进

> LLM 能回答问题，但 Agent 能自主做事。两者之间差了什么？本文从 Agent 的核心定义出发，拆解感知-规划-执行-反馈循环，逐层分析 ReAct、Plan-and-Execute、Reflection 三大主流设计模式。

---

## 一、Agent 到底是什么

### 1.1 Agent vs LLM vs Chatbot

很多人把"接了大模型的聊天机器人"等同于 Agent，这是个误解。三者的区别：

| | Chatbot | LLM | Agent |
|---|---------|-----|-------|
| 输入 | 用户消息 | Prompt + Context | 目标 / 任务 |
| 输出 | 回复文本 | 文本补全 | 行动 + 结果 |
| 能力边界 | 对话 | 文本生成 | 使用工具、修改环境 |
| 决策方式 | 无（或规则） | 无 | 自主判断下一步做什么 |
| 典型例子 | 客服机器人 | GPT-4 单次调用 | AutoGPT、Devin、Cursor Agent |

本质区别在于 **自主决策能力**：
- LLM 是被动的：你问，它答。
- Agent 是主动的：你给目标，它自己决定先搜什么、再调哪个 API、最后怎么整合。

### 1.2 核心四组件

任何 Agent 系统都由四个组件构成：

```
┌─────────────────────────────────────────┐
│                  Agent                   │
│  ┌──────────┐  ┌──────────────────────┐ │
│  │  LLM     │  │  Tools / Actions     │ │
│  │  (大脑)  │  │  (手脚)              │ │
│  └────┬─────┘  └──────────┬───────────┘ │
│       │                   │             │
│  ┌────┴───────────────────┴───────────┐ │
│  │          Planning (规划)           │ │
│  └────────────────────────────────────┘ │
│  ┌────────────────────────────────────┐ │
│  │          Memory (记忆)             │ │
│  └────────────────────────────────────┘ │
└─────────────────────────────────────────┘
```

- **LLM (大脑)**：负责推理、规划、决策。不是简单的文本生成，而是要理解当前状态、判断该用什么工具、评估结果是否达成目标
- **Tools (手脚)**：搜索 API、代码执行器、数据库查询、文件操作……Agent 通过各种工具与外部世界交互
- **Memory (记忆)**：短期记忆（上下文窗口）、长期记忆（向量库/数据库），让 Agent 能从历史中学习
- **Planning (规划)**：将大目标拆解为子任务，编排执行顺序，处理依赖关系，在失败时调整策略

### 1.3 核心循环：感知 → 规划 → 执行 → 反馈

无论哪种 Agent 架构，底层的运行循环都是相通的：

```
目标输入
   ↓
┌──────────────────────────┐
│  1. 感知 (Observe)       │  ← 读上下文、工具返回结果、环境状态
│  2. 思考 (Think)         │  ← LLM 推理：现在该干什么？
│  3. 行动 (Act)           │  ← 调用工具 / 输出结果
│  4. 反馈 (Feedback)      │  ← 行动结果注入上下文
└──────────────────────────┘
   ↓
判断目标是否达成？
  否 → 回到步骤 1
  是 → 输出最终结果
```

这个循环看起来简单，但设计的核心问题是：**每一步 Thinking 到底"该想什么"、"该怎么想"**。这直接引出了不同的设计模式。

## 二、ReAct 模式 —— Agent 的基石

### 2.1 为什么 ReAct 而不是纯 CoT

CoT (Chain-of-Thought) 让 LLM 在回答前"多想几步"，大幅提升了推理能力。但 CoT 的问题是：**它只能想，不能做**。

LLM 的幻觉在 CoT 下依然存在——它不知道某个日期是不是周三，就只能编。ReAct (Reasoning + Acting) 的核心洞察是：**让推理和行动交替进行**。

推理告诉你"我需要知道什么"，行动去获取真实信息，真实信息修正后续推理——形成一个闭环。

### 2.2 ReAct 的执行范式

ReAct 的标准输出格式：

```
Thought: 分析当前状态，决定下一步做什么
Action: 要调用的工具名称
Action Input: 传给工具的参数
Observation: 工具返回的结果
... (重复 Thought → Action → Observation)
Thought: 信息已足够，给出最终答案
Final Answer: 最终回复
```

一个具体例子（查天气并判断是否需要带伞）：

```
Thought: 用户想知道今天是否需要带伞，我需要查询今天的天气
Action: search_weather
Action Input: {"city": "北京", "date": "2026-07-29"}

Observation: {"weather": "中雨", "temperature": "24°C-29°C", "humidity": "85%"}

Thought: 天气是中雨且湿度高，所以今天需要带伞
Final Answer: 今天北京有中雨，湿度 85%，强烈建议带伞出门。
```

关键设计点：
- **每轮只做一个行动**，行动结果作为下一轮的输入。这保证了 Agent 的决策始终基于"真实信息"，而不是幻觉
- **Thought 是透明的**：用户/debugger 能看到 Agent 每一步的推理过程，这对可解释性和调优至关重要
- **终止条件清晰**：要么输出 Final Answer，要么在无可用行动时报错

### 2.3 ReAct 的提示词工程

ReAct 的 prompt 模板通常包含以下要素：

```
System Prompt:
你是一个可以通过工具完成任务的 AI 助手。
你可以使用以下工具：
- search(query: str): 搜索互联网信息
- calculator(expression: str): 计算数学表达式
- get_weather(city: str): 查询城市天气

请严格遵循以下格式：
Thought: [你的推理过程]
Action: [工具名]
Action Input: [工具参数 JSON]
Observation: [工具返回]

当你获得足够信息后回答：
Final Answer: [最终答案]

User: 明天上海会下雨吗？如果下雨，比北京冷多少度？
```

**Prompt 技巧**：
- **few-shot 示例**：在 system prompt 中放 1-2 个完整的 ReAct 执行示例，比规则描述更有效
- **工具描述精确化**：参数名要有含义（`city_name` 优于 `param1`），description 写清楚"什么时候该用这个工具"
- **错误恢复指引**：告诉 Agent "如果工具返回 error，请分析错误信息并调整参数重试"

### 2.4 ReAct 的局限

- **单步串行**：每轮只做一个动作，复杂任务需要很多轮，token 消耗大
- **缺乏全局规划**：走一步看一步，可能在非关键分支浪费大量步骤
- **没有自我纠错机制**：如果某一步的推理方向错了，ReAct 本身无法"意识到自己跑偏了"

正是这些局限催生了更高级的模式。

## 三、Plan-and-Execute 模式

### 3.1 核心思想：先规划，后执行

ReAct 是"边走边想"，Plan-and-Execute 是"想好了再走"。

```
用户目标
   ↓
┌──────────────┐
│  Planner     │  ← LLM 制定完整执行计划
│  (规划者)    │     输出：步骤1 → 步骤2 → 步骤3 → ...
└──────┬───────┘
       ↓ 计划
┌──────────────┐
│  Executor    │  ← 逐步骤执行，可选：每步执行后汇报
│  (执行者)    │
└──────────────┘
       ↓
   最终结果
```

### 3.2 为什么要分离规划和执行

**1. 全局视角**：规划阶段可以"看到全貌"，识别任务之间的依赖关系。比如"需要先从 A 数据库取用户 ID，再根据 ID 去 B 系统查订单"——Planner 一次性理清这个依赖链。

**2. 降低 LLM 调用成本**：ReAct 每步都要调 LLM 做 Thought，而 Plan-and-Execute 只在规划阶段调用一次 LLM，执行阶段可以是纯代码逻辑。对于步骤多但确定性高的任务，token 消耗大幅降低。

**3. 可中断与可恢复**：计划是结构化的，执行到一半可以暂停、人工审核、再继续。

### 3.3 实现示例

```
Planner 输出:
{
  "goal": "分析 GitHub 上 pytorch 项目最近一周的热门 issue",
  "steps": [
    {"id": 1, "action": "search_issues", "args": {"repo": "pytorch/pytorch", "since": "2026-07-22"}},
    {"id": 2, "action": "filter_by_reactions", "args": {"min_reactions": 10}, "depends_on": [1]},
    {"id": 3, "action": "summarize", "args": {}, "depends_on": [2]}
  ]
}
```

Executor 按依赖顺序执行，步骤 2 的输入是步骤 1 的输出。

### 3.4 如何处理计划出错

计划不可能总是完美的。主流的补救方式：

- **Re-planning**：执行某步骤失败时，把已完成的步骤结果 + 失败信息 + 剩余目标一起交还给 Planner，让它重新规划
- **Conditional Plan**：规划时考虑分支："如果步骤 2 返回空，跳转到步骤 4"
- **Plan + ReAct 混合**：规划出骨架，执行每个步骤时用 ReAct 做局部探索 —— 这是 LangGraph 等框架的常见做法

## 四、Reflection / Reflexion 模式

### 4.1 核心思想：让 Agent 评价自己

人类的做事方式不是"做了就完了"，做完之后会反思："刚才哪里做得不好？下次怎么改进？"

Reflection 模式把这个过程形式化——Agent 完成一次执行后，由另一个 LLM 调用（或同一 LLM 换角色）对执行过程做评估，给出改进建议。然后带着改进建议重新执行。

### 4.2 Reflexion 的三角色架构

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│    Actor     │────▶│  Evaluator   │────▶│   Self-Refl  │
│   (执行者)   │     │   (评估者)   │     │  (反思存储)  │
└──────────────┘     └──────────────┘     └──────┬───────┘
       ▲                                         │
       └─────────────────────────────────────────┘
                    反馈循环
```

- **Actor**：实际执行任务（可以用 ReAct 或 Plan-Execute）
- **Evaluator**：拿到执行轨迹后，从多个维度评价：结果是否正确？执行是否高效？哪里可以改进？
- **Self-Reflection**：将评估结果存储为"经验"，Actor 下一次执行时会被注入这些经验

### 4.3 评估的维度

Evaluator 通常会检查：

```
1. 最终结果是否正确？（任务达成率）
2. 执行效率如何？（是否走了多余步骤、调用了不必要的工具）
3. 推理逻辑有无漏洞？（Thought 是否基于正确的假设）
4. 工具使用是否准确？（参数是否正确、是否选错了工具）
```

评估结果压缩为"经验"存入记忆：

```
经验 1：查询天气时，如果用户没有指定具体日期，应该默认查"今天"而不是报错。
经验 2：搜索结果太多（>20条）时，先用 filter 缩小范围再总结。
```

### 4.4 Reflection 的变体

**Self-Refine**：Actor 和 Evaluator 是同一个 LLM，通过 prompt 切换角色。简单有效，对编码/写作类任务尤其好。

**Language Agent Tree Search (LATS)**：将树搜索引入 Agent 决策——每个决策点展开多个分支，用 LLM 评估每个分支的预期价值，选择最优路径。思路类似 AlphaGo 的 MCTS，但评估函数换成了 LLM。

**CRITIC**：让 Agent 和外部知识源（代码执行器、搜索引擎）交互来做验证。比如 Agent 声称代码没问题 → 自动执行代码 → 结果不对 → 用报错信息修正。

### 4.5 Reflection 的实战提示词

```
Evaluator Prompt:
你是一个严格的质量审查员。请审查以下任务的执行轨迹：

[执行轨迹]

请从以下维度给出评价：
1. 最终结果是否符合用户目标？
2. 执行步骤是否有冗余或遗漏？
3. 如果结果不满意，具体哪一步可以怎么改进？

请给出简短的"改进建议"，这些建议将在下次执行时提供给 Agent。
```

## 五、模式对比与选择

| 维度 | ReAct | Plan-Execute | Reflexion |
|------|-------|-------------|-----------|
| 核心思路 | 边走边想 | 先规划后执行 | 边做边反思 |
| 规划方式 | 逐步推理 | 全局规划 | 渐进改进 |
| LLM 调用次数 | 多（每步一次） | 少（规划 + 关键点） | 多（加评估轮次） |
| 适合任务 | 探索型、信息检索 | 步骤确定、依赖明确 | 需要高质量输出、迭代改进 |
| 效率 | 低（串行 + 多轮） | 高（并行执行） | 低（多次重试） |
| Token 消耗 | 高 | 中 | 高 |
| 可解释性 | 好（每步可见） | 好（计划可见） | 最好（轨迹 + 评估） |

**选择建议**：
- 任务简单、步骤 < 5 步 → **ReAct** 足够，不要过度设计
- 步骤多但有固定流程 → **Plan-Execute**，省 token 且可中断审核
- 对输出质量要求极高、可接受多次重试 → **Reflexion**，尤其适合代码生成、数学推理
- 生产环境推荐 → **Plan + ReAct 混合**：骨架用规划，细节用 ReAct 探索

## 六、Agent 自主性等级

从工程角度看，Agent 的自主程度是一个连续谱：

| 等级 | 描述 | 举例 |
|------|------|------|
| L0: 无自主 | 人类做所有决策 | 传统程序 |
| L1: 建议 | AI 提建议，人类决策 | GitHub Copilot 补全 |
| L2: 执行 | 人类定步骤，AI 执行 | "帮我查这 10 个股票的收盘价" |
| L3: 规划 | AI 定步骤，人类审批执行 | "帮我分析竞品定价" → 人确认方案 → 执行 |
| L4: 自主 | AI 自己规划并执行 | AutoGPT、Devin |
| L5: 完全自主 | AI 自主设定目标 | （目前不存在） |

**生产环境的实用主义**：绝大多数场景应该停在 L2-L3。L4 在生产中不可控（成本、安全、可靠性都难保证），核心业务链路一律加 **Human-in-the-loop**——关键决策点暂停等人工确认。
