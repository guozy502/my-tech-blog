# 历史背景——DDD 为什么诞生？

2003 年，Eric Evans 出版了《领域驱动设计》。这本书是在他多年参与复杂企业软件开发后的反思——他发现了一个反复出现的问题：**技术团队和业务团队说不同的语言，业务规则在代码中被分散到 Controller/Service/DAO 各处，半年后没人知道"为什么这个 if 要放在这里"。**

DDD 的核心思想只有一句话：**让代码模型和业务领域的模型对齐。** 不是技术去"翻译"业务，而是业务直接体现在代码里——同一个词在代码和业务中表达同一个含义。Evans 把这种方法论分成两个层面：**战略设计**（怎么把大系统拆成小系统）和**战术设计**（在一个小系统内部怎么组织代码）。

理解 DDD 的关键是先承认一个前提：**不是所有项目都需要 DDD。** 如果你做的是"接收 JSON → 查 MySQL → 返回 JSON"，DDD 带来的复杂度大于收益。DDD 的价值场景是"复杂的业务规则需要在长期维护中保持可理解性"。

# 一、战略设计——怎么把大系统拆成"相对独立的小系统"

## 1.1 限界上下文——同一个词，不同含义

```
现实中的例子：电商系统

  订单上下文中的"商品"：
    关心 → 价格、SKU、库存状态、促销信息
    不关心 → 商品重量、包装尺寸、危险品分类

  物流上下文中的"商品"：
    关心 → 重量、体积、是否需要冷链、是否危险品
    不关心 → 促销价、库存状态、关联推荐

  同一个物理商品，在不同上下文中是不同的"模型"
  → 如果你做一个"统一商品模型"（包含所有字段）→ 两个上下文耦合在一起
  → 物流改了一个字段 → 订单那边可能被影响 → 需要联调 → 需要一起发布
```

**限界上下文（Bounded Context）**：一个模型在其中"有效且含义明确"的边界。上下文内部有统一的语言（统一语言 Ubiquitous Language），团队用同样的词汇讨论业务和代码。限界上下文 = 你画业务流程图时圈出来的那个"这个和那个是两件事"的圈。

## 1.2 上下文映射——上下文之间的关系

系统由多个限界上下文组成。它们之间怎么交互？

```
① 共享内核（Shared Kernel）：
    两个上下文共享同一份模型代码
    例：订单和支付共享"Money"值对象（金额 + 币种）

    优点：减少重复
    风险：共享部分的改动影响双方 → 需要双方团队协商变更

② 客户-供应商（Customer-Supplier）：
    上游（供应商）定义接口和模型，下游（客户）适配
    例：支付网关（供应商）定义 PayRequest/PayResponse → 
        订单系统（客户）来适配

    上游有话语权——下游需要迁就上游的接口

③ 防腐层（ACL, Anti-Corruption Layer）：
    下游用自己的模型翻译上游的模型
    例：订单系统不直接用支付网关的 PayRequest，
        而是在自己的边界内定义一个 PaymentService，
        内部把 Order → 翻译成 PayRequest → 调支付网关 → 
        收到 PayResponse → 翻译成 PaymentResult

    ACL 的最大价值：隔离外部模型的变化
    支付网关升级 API → 只改 ACL，订单的其他代码不受影响

④ 各行其道（Separate Ways）：
    两个上下文不直接通信，通过 MQ/Event 异步解耦
    例：订单完成 → 发 OrderCompletedEvent → 
        积分系统消费 → 给用户加积分
    订单不需要"知道"积分系统的存在
```

**面试怎么用这个知识点**：面试官问"你怎么拆分微服务"——不要上来就说"按功能拆"，而是说"先识别限界上下文，再确定上下文之间的映射关系。不是所有上下文都要独立部署——有些是 ACL 就可以。决定的依据是：两个上下文的变更频率是否一致，团队是否独立，数据是否应该独立。"

# 二、战术设计——在一个限界上下文内部怎么组织代码

## 2.1 聚合——事务一致性 + 并发控制的边界

```
问题：Order 和 OrderLineItem 的关系？
  删除 Order → 其所有 OrderLineItem 也应该一起删除
  修改 OrderLineItem 的数量 → 必须保证 Order 的总金额也被更新

聚合：把"必须一起保持一致"的对象打包成一个整体
  Order（聚合根） → 外部访问的唯一入口
    └── OrderLineItem（聚合内部实体）

聚合的四个设计原则：
  ① 聚合根是唯一入口
     外部永远通过 OrderRepository 获取 Order，然后通过 order.addItem() 来添加
     不能直接从外部"拿出一个 OrderLineItem 来改"

  ② 小聚合优于大聚合
     Order 和 Product 是独立的聚合——Order 只持有 productId（ID 引用），不持有 Product 对象
     如果 Order 持有了 Product → 改 Product 时需要锁住所有包含它的 Order → 并发冲突指数级增长

  ③ 通过 ID 引用其他聚合
     Order 存的是 productId（Long），不是 Product 对象
     跨聚合访问 → 通过 Repository 用 ID 去查

  ④ 一个事务只修改一个聚合
     Order 支付 → 只改 Order 聚合，不改 Product 聚合
     Product 库存的更新 → 通过 Event 异步通知 → 最终一致性
     这就是为什么"秒杀"需要最终一致性而不是分布式事务——
     一个事务内同时锁 Order 和 Product 会导致并发崩溃
```

## 2.2 实体 vs 值对象——这是 DDD 中最实用的分类

```
实体的判断标准：你关心"这是哪一个"
  例：User(id=123) 改名了 → 还是同一个 User（id 不变）

值对象的判断标准：你关心"它是什么"
  例：Money(100, "CNY") → 金额和币种共同定义了这个值
      Money(100, "CNY") 和 Money(100, "USD") 是不同的
      Money 没有 id → 它的"相等性"由所有属性决定

为什么分这个？
  实体需要管理生命周期（创建、修改、删除）
  值对象可以随意创建和丢弃（它们没有身份，只描述一个值）
  
  值对象必须不可变（Immutable）
  → Money(100, "CNY").add(Money(50, "CNY")) → 返回新的 Money(150, "CNY")
  → 不修改原来的 Money

判例练习：
  Address（城市/街道/邮编）→ 实体还是值对象？
  答案：取决于上下文！
    在用户上下文中，Address 通常是值对象（只是用户的一个属性）
    在物流公司上下文中，Address 可能是实体（需要唯一标识一个配送点）
```

## 2.3 领域服务——不属于任何实体的业务逻辑

```
有些业务逻辑不属于任何一个实体：
  例：转账——从 Account A 扣钱，给 Account B 加钱
  这个逻辑应该放在 Account A 上（A.transferTo(B, amount)）还是 Account B 上（B.receiveFrom(A, amount)）？
  → 都不合适。它是两个账户之间的事。

领域服务：把这种"发生在多个实体之间"的业务逻辑封装在一个无状态的 Service 中
  TransferService.transfer(fromAccount, toAccount, amount)

判断标准——这个逻辑应该放哪？
  ① 只涉及一个实体 → 放在实体方法中（如 Order.addItem(item)）
  ② 涉及多个实体 → 放在领域服务中（如 TransferService）
  ③ 需要查外部数据/调外部 API → 放在应用服务中（Application Service, 编排调用）
```

# 三、DDD 不是银弹——什么时候不该用

```
✅ 适合 DDD 的场景：
  - 核心领域复杂（不是技术复杂，是业务规则复杂）
  - 系统需要长期维护和演化（至少 2-3 年以上）
  - 技术团队和业务团队可以紧密沟通
  - 例：交易系统、风险管理、保险理赔、供应链调度

❌ 不适合 DDD 的场景：
  - 简单的 CRUD 系统（增删改查，没有复杂业务规则）
  - 纯技术驱动的系统（如网关、消息转发、代理）
  - 团队规模小且业务逻辑不多
  - 短期项目（MVP → 可能需要重构，但DDD的重构成本高于代码层面的重构）

引入 DDD 的真实成本：
  - 需要业务专家和开发团队的大量沟通（"事件风暴"建模需要半天到两天）
  - 代码量增加——值对象、领域服务、Repository 接口、防腐层都增加类和文件
  - 新人培训成本——传统分层的 Controller-Service-DAO 比 DDD 的聚合-值对象-领域服务好理解得多
```

# 四、总结

| 概念 | 一句话 | 判断标准 |
|------|--------|---------|
| **限界上下文** | 一个模型有效的边界 | "这个词在这里是这个意思吗？" |
| **上下文映射** | 上下文之间的关系 | "谁定义接口？谁适配谁？可以互不干扰吗？" |
| **聚合** | 事务一致性的最小单位 | "这两条数据必须一起改吗？" |
| **实体** | 有唯一标识的对象 | "我关心这是哪一个" |
| **值对象** | 不可变、无 ID 的值 | "我关心它是什么" |
| **领域服务** | 跨实体的业务逻辑 | "这个操作属于哪个对象？都不属于？" |
| **防腐层** | 隔离外部模型变更 | "外部 API 变了只改这一层" |
