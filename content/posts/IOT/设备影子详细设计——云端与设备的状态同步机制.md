# 设备影子详细设计——云端与设备的状态同步机制

> 设备影子（Device Shadow）是物联网平台最精巧的设计之一。你给一台离线的空调发了一条"设温 26°C"的指令，它怎么在三天后上线时准确执行？本文从数据结构、同步机制、并发控制、可靠性保障四个维度，拆解设备影子的完整设计。

---

## 一、en

### 1.1 三个核心痛点

**指令的时空解耦**：发送指令时设备离线 → 指令不能丢 → 设备上线后必须知道自己"欠了"什么指令。

**状态的单一真相源**：云端说温度该 26°C，设备说实际是 24°C → 两台都有道理但不一样，以谁为准？影子说：desired 归云端管，reported 归设备管，差异就是待执行的 delta。

**应用层无需关心设备在线状态**：业务代码只管"把空调设成 26°C"——影子自己处理"设备在线就下发、不在线就缓存"的逻辑。业务方看到的永远是一个 JSON 对象，不关心设备实际连没连着。

### 1.2 核心数据模型

```json
{
  "state": {
    "desired": {
      "power": "ON",
      "temperature": 26,
      "mode": "COOL"
    },
    "reported": {
      "power": "OFF",
      "temperature": 24,
      "mode": "COOL"
    }
  },
  "metadata": {
    "desired": {
      "power": {"timestamp": 1751412000},
      "temperature": {"timestamp": 1751412000}
    },
    "reported": {
      "power": {"timestamp": 1751410000},
      "temperature": {"timestamp": 1751410000}
    }
  },
  "version": 17,
  "timestamp": 1751412000
}
```

三个核心字段：
- **desired**：云端期望的状态。应用层往这里写，设备有义务执行
- **reported**：设备上报的实际状态。设备往这里写，云端和应用层从这里读
- **delta**：不直接存储，通过 `desired - reported` 实时计算。设备上线时拿到 delta，执行差异部分
- **version**：乐观锁版本号。每次修改必须 CAS，防止并发覆盖
- **metadata**：每个字段的最后修改时间戳，用于排查"这条指令到底是什么时候下的"

## 二、影子的存储设计

### 2.1 分层存储策略

设备影子需要**高频读写**（设备上报状态）、**低延迟查询**（APP 打开看设备状态）、**持久化保证**（指令不能丢）。

```
写入路径:
  APP 设 desired → 写 Redis → 异步写 MySQL（持久化）
  
读取路径:
  查影子 → 读 Redis → 命中返回 → 未命中 → 读 MySQL → 预热到 Redis
  
设备同步:
  设备连上 → 读 Redis 影子 → 计算 delta → 下发
```

Redis 做主存储（满足高频低延迟），MySQL 做持久化兜底（防止 Redis 故障丢数据）。不是"Redis 缓存 + MySQL 主存储"的模式——影子本质上是一个高频读写的 KV 文档，Redis 完全能胜任主存储的角色，MySQL 是异步备份。

### 2.2 Redis 数据结构

```
Key:   shadow:{productKey}:{deviceId}
Type:  Hash
Value:
  desired_json   → '{"power":"ON","temperature":26,"mode":"COOL"}'
  reported_json  → '{"power":"OFF","temperature":24,"mode":"COOL"}'
  version        → '17'
  updated_at     → '1751412000'
```

Hash 而不是 String 的原因：`desired` 和 `reported` 经常独立更新。设备只更新 `reported`，业务只更新 `desired`——用 Hash 可以原子更新其中一个字段而不影响另一个。

### 2.3 MySQL 表结构

```sql
CREATE TABLE device_shadow (
    id             BIGINT PRIMARY KEY AUTO_INCREMENT,
    product_key   VARCHAR(32)  NOT NULL,
    device_id      VARCHAR(64)  NOT NULL,
    desired_json   TEXT,                      -- 期望状态 JSON
    reported_json  TEXT,                      -- 上报状态 JSON
    version        INT          NOT NULL DEFAULT 0,
    created_at     DATETIME     NOT NULL,
    updated_at     DATETIME     NOT NULL,
    UNIQUE KEY uk_device (product_key, device_id)
);

-- 操作日志（用于审计和回溯）
CREATE TABLE shadow_operation_log (
    id             BIGINT PRIMARY KEY AUTO_INCREMENT,
    product_key   VARCHAR(32)  NOT NULL,
    device_id      VARCHAR(64)  NOT NULL,
    op_type        VARCHAR(16)  NOT NULL,     -- UPDATE_DESIRED / UPDATE_REPORTED / DELETE
    op_content     JSON         NOT NULL,     -- 变更内容
    op_source      VARCHAR(32)  NOT NULL,     -- APP / DEVICE / RULE_ENGINE / ADMIN
    old_version    INT          NOT NULL,
    new_version    INT          NOT NULL,
    created_at     DATETIME     NOT NULL,
    INDEX idx_device_time (product_key, device_id, created_at)
);
```

操作日志表是排查"谁在什么时候改了什么"的唯一手段。线上出问题时——"用户说 APP 显示的温度和空调面板不一样"——从 `shadow_operation_log` 可以精确追溯到每次修改的来源和时间。

## 三、核心流程

### 3.1 设备上线同步

```
┌──────────┐         ┌──────────┐         ┌──────────┐
│   设备    │         │  Broker  │         │  影子服务 │
└────┬─────┘         └────┬─────┘         └────┬─────┘
     │  CONNECT           │                    │
     │───────────────────▶│                    │
     │                    │  同步影子请求       │
     │                    │───────────────────▶│
     │                    │                    │
     │                    │    读 Redis 影子   │
     │                    │◀───────────────────│
     │                    │  {desired, reported, version}
     │                    │                    │
     │  下发 delta (差异)  │                    │
     │◀──────────────────│                    │
     │  delta = desired - reported            │
     │  delta: {"power":"ON", "temperature":26}
     │                                         │
     │  执行差异: 开机 + 设温 26°C              │
     │                                         │
     │  上报新 reported                        │
     │───────────────────▶                     │
     │  {"power":"ON","temperature":26,        │
     │   "mode":"COOL"}                       │
     │                    │  更新 reported     │
     │                    │───────────────────▶│
```

**Delta 计算的实现**：

```java
public Map<String, Object> calculateDelta(JsonNode desired, JsonNode reported) {
    Map<String, Object> delta = new HashMap<>();
    
    Iterator<String> fieldNames = desired.fieldNames();
    while (fieldNames.hasNext()) {
        String field = fieldNames.next();
        JsonNode desiredValue = desired.get(field);
        
        if (!reported.has(field)) {
            // reported 中没有这个字段 → 设备从未上报过 → 需要执行
            delta.put(field, desiredValue);
        } else if (!desiredValue.equals(reported.get(field))) {
            // 值不同 → 需要执行
            delta.put(field, desiredValue);
        }
        // 值相同 → 不需要执行，不加入 delta
    }
    return delta;
}
```

这个算法的洞察是：**只下发差异，不下发全量 desired**。设备每次需要执行的指令量最小化，弱网环境下尤其重要。

### 3.2 APP 设置 desired

```java
@Service
public class ShadowService {
    
    private RedisTemplate<String, String> redis;
    private ShadowLogMapper logMapper;
    private MqttPublisher mqttPublisher;
    
    /**
     * 更新 desired —— APP / 规则引擎 / 管理后台的通路
     */
    public ShadowUpdateResult updateDesired(
            String productKey, String deviceId, 
            Map<String, Object> desiredFields) {
        
        String shadowKey = shadowRedisKey(productKey, deviceId);
        
        // 1. CAS 更新 Redis
        // Lua 脚本: 读取当前 version → 合并 desired → version+1 → 写回
        String luaScript = """
            local shadowKey = KEYS[1]
            local desiredUpdates = cjson.decode(ARGV[1])
            
            -- 读取当前影子
            local currentVersion = tonumber(redis.call('hget', shadowKey, 'version') or '0')
            local currentDesired = cjson.decode(redis.call('hget', shadowKey, 'desired_json') or '{}')
            local currentReported = redis.call('hget', shadowKey, 'reported_json') or '{}'
            
            -- 合并 desired (增量更新)
            for field, value in pairs(desiredUpdates) do
                currentDesired[field] = value
            end
            
            -- CAS 写入
            local newVersion = currentVersion + 1
            redis.call('hset', shadowKey, 'desired_json', cjson.encode(currentDesired))
            redis.call('hset', shadowKey, 'version', tostring(newVersion))
            redis.call('hset', shadowKey, 'updated_at', tostring(ARGV[2]))
            
            return cjson.encode({
                version = newVersion,
                desired = currentDesired,
                reported = currentReported
            })
            """;
        
        String result = (String) redis.execute(
            new DefaultRedisScript<>(luaScript, String.class),
            Collections.singletonList(shadowKey),
            JsonUtils.toJson(desiredFields),
            String.valueOf(System.currentTimeMillis() / 1000)
        );
        
        ShadowSnapshot snapshot = JsonUtils.fromJson(result, ShadowSnapshot.class);
        
        // 2. 异步持久化到 MySQL
        CompletableFuture.runAsync(() -> {
            shadowMapper.upsert(productKey, deviceId, 
                snapshot.getDesired(), snapshot.getReported(), snapshot.getVersion());
            logMapper.insert(buildLog(productKey, deviceId, 
                "UPDATE_DESIRED", "APP", desiredFields, snapshot));
        });
        
        // 3. 尝试实时下发
        // 设备在线 → 立即下发 delta；不在线 → 等待设备下次上线同步
        boolean deviceOnline = deviceSessionService.isOnline(productKey, deviceId);
        if (deviceOnline) {
            Map<String, Object> delta = calculateDelta(
                snapshot.getDesired(), snapshot.getReported());
            if (!delta.isEmpty()) {
                mqttPublisher.sendCommand(productKey, deviceId, 
                    new ShadowDeltaCommand(snapshot.getVersion(), delta));
            }
        }
        
        return new ShadowUpdateResult(snapshot.getVersion(), deviceOnline);
    }
}
```

三个设计要点：
- **增量合并**：APP 只传要改的字段（如 `{"temperature": 26}`），不传整个 desired——避免了并发修改时互相覆盖
- **CAS 原子操作**：Lua 脚本保证读-改-写是原子的。多个 APP 同时对同一设备发指令，version 机制保证后执行的写失败，必须重试
- **尽力实时下发**：设备在线时直接下发 delta，不在线时不强求——设备上线后同步影子会自然拿到差异

### 3.3 设备上报 reported

```java
public void updateReported(
        String productKey, String deviceId,
        Map<String, Object> reportedFields) {
    
    String shadowKey = shadowRedisKey(productKey, deviceId);
    
    String luaScript = """
        local shadowKey = KEYS[1]
        local reportedUpdates = cjson.decode(ARGV[1])
        
        local currentVersion = tonumber(redis.call('hget', shadowKey, 'version') or '0')
        local currentDesired = cjson.decode(redis.call('hget', shadowKey, 'desired_json') or '{}')
        local currentReported = cjson.decode(redis.call('hget', shadowKey, 'reported_json') or '{}')
        
        -- 合并 reported
        for field, value in pairs(reportedUpdates) do
            currentReported[field] = value
        end
        
        local newVersion = currentVersion + 1
        redis.call('hset', shadowKey, 'reported_json', cjson.encode(currentReported))
        redis.call('hset', shadowKey, 'version', tostring(newVersion))
        redis.call('hset', shadowKey, 'updated_at', tostring(ARGV[2]))
        
        -- 计算新的 delta: 上报后 desired 中的哪些值还没达成？
        local remainingDelta = {}
        for field, value in pairs(currentDesired) do
            if currentReported[field] == nil then
                remainingDelta[field] = value
            elseif currentReported[field] ~= value then
                remainingDelta[field] = value
            end
        end
        
        return cjson.encode({
            version = newVersion,
            desired = currentDesired,
            reported = currentReported,
            hasRemainingDelta = next(remainingDelta) ~= nil,
            remainingDelta = remainingDelta
        })
        """;
    
    String result = (String) redis.execute(
        new DefaultRedisScript<>(luaScript, String.class),
        Collections.singletonList(shadowKey),
        JsonUtils.toJson(reportedFields),
        String.valueOf(System.currentTimeMillis() / 1000)
    );
    
    ShadowSyncResult syncResult = JsonUtils.fromJson(result, ShadowSyncResult.class);
    
    // 异步持久化
    CompletableFuture.runAsync(() -> {
        shadowMapper.upsert(productKey, deviceId, 
            syncResult.getDesired(), syncResult.getReported(), syncResult.getVersion());
    });
    
    // 如果还有未达成的 desired → 下发剩余 delta
    if (syncResult.isHasRemainingDelta()) {
        mqttPublisher.sendCommand(productKey, deviceId,
            new ShadowDeltaCommand(syncResult.getVersion(), syncResult.getRemainingDelta()));
    }
    
    // 推送状态变更通知给 APP（WebSocket/长轮询）
    pushShadowUpdate(productKey, deviceId, syncResult);
}
```

设备上报时的特殊处理：**自动计算剩余 delta**。设备可能因为各种原因没完全达成 desired（如空调设定 26°C 但当前 27°C 还在降温中），reported 更新后如果跟 desired 还有差距，影子服务自动再下发一次剩余 delta——形成"上报 → 对比 → 再下发"的闭环。

## 四、并发控制

### 4.1 并发场景分析

```
场景 1: APP A 和 APP B 同时设温度
  A: temperature=26  →  shadow  {desired: {..., temperature: 26}}
  B: temperature=28  →  shadow  {desired: {..., temperature: 28}}
  最终一致即可，谁后写谁生效——version CAS 自然保证了不会丢

场景 2: 设备上报和 APP 写同时发生
  APP: 更新 desired {temperature: 26}
  设备: 上报 reported {temperature: 25}
  两者操作不同字段 → Hash 结构独立 → 不冲突

场景 3: 影子服务下发 delta 后等设备确认期间，APP 又改了 desired
  第一次下发: delta={temperature: 26}
  APP 改成:   desired.temperature = 28
  设备确认:    reported.temperature = 26
  → 影子检测到 reported(26) ≠ desired(28)
  → 自动再次下发 delta={temperature: 28}
```

### 4.2 Version 的 CAS 保障

```java
// 并发冲突时的重试逻辑
public ShadowUpdateResult updateDesiredWithRetry(
        String productKey, String deviceId,
        Map<String, Object> desiredFields, int maxRetries) {
    
    for (int i = 0; i < maxRetries; i++) {
        try {
            return updateDesired(productKey, deviceId, desiredFields);
        } catch (ShadowVersionConflictException e) {
            // 版本冲突：读最新版本后重试
            if (i == maxRetries - 1) {
                throw new ShadowUpdateException(
                    "影子更新失败，version 冲突超过最大重试次数");
            }
            // 短暂随机退避后重试
            Thread.sleep(ThreadLocalRandom.current().nextLong(10, 50));
        }
    }
    throw new ShadowUpdateException("unreachable");
}
```

为什么不用分布式锁（Redis SETNX）而是用 CAS？因为影子的并发冲突场景是"多个写方同时更新同一个对象的不同字段"——用锁会让这些操作完全串行化，而 CAS + 增量合并可以让它们并发执行。

## 五、可靠性保障

### 5.1 下发指令的 Exactly-Once 语义

网络的不可靠性意味着同一条 delta 指令可能被设备收到多次。Exactly-Once 的实现：

```java
// 下发 delta 时带 commandId（全局唯一）
public class ShadowDeltaCommand {
    private String commandId;       // UUID，全局唯一
    private int shadowVersion;      // 影子版本号
    private Map<String, Object> delta;
}

// 设备端处理
// 1. 记录最后处理的 commandId（存在 Flash 或 RTC 备份 RAM）
// 2. 收到新 command → 如果 commandId == 最后处理的 → 忽略（幂等）
// 3. 如果 commandId 不同但 shadowVersion <= 已执行的版本 → 忽略
// 4. 否则 → 执行 → 记录 commandId + shadowVersion → 上报结果
```

两个维度的去重：**commandId + shadowVersion**。commandId 负责精确去重（同一条指令重复收到），shadowVersion 负责版本去重（旧版本指令迟到被新版本覆盖后无视）。

### 5.2 设备离线期间的指令合并

设备离线 3 天，业务方在这期间发了 10 条指令：
- `第 1 条: temperature=26`
- `第 2 条: temperature=28`
- `第 3 条: power=OFF`
- ...
- `第 10 条: power=ON, temperature=26, mode=COOL`

影子设计的关键洞察：**设备不需要逐条执行这 10 条指令**。上线时只计算最终 desired 和当前 reported 的 delta——一次性把"你现在应该是什么状态"告诉设备。中间 9 条指令的"过程"对设备无意义，只关心"结果"。

合并逻辑天然由 desired 的覆盖写入实现——每个字段的最新值覆盖旧值，设备上线时只看到最终状态。这也印证了为什么 desired 必须是"状态"而不是"命令"——"设温 26°C"是状态（可覆盖），"开锁"是命令（不可覆盖，必须逐条执行）。

### 5.3 异常场景处理

**设备上报 desired 已达成，但实际又变了**：设备的温度传感器有精度误差——设 26°C 但实际稳定在 26.3°C，设备上报 26°C（四舍五入），desired 也是 26°C，影子判定"已达成"。但实际上 app 用户可能会看到 26.3°C 差异。这个不靠影子解决——依赖设备上报的精度和 APP 端的显示策略（保留一位小数 + 容忍 ±0.5°C 波动不给用户展示微变化）。

**影子数据丢失（Redis 故障）**：
- 优先从 MySQL 恢复
- 极限情况（Redis + MySQL 同时故障的概率极低）：设备持有的上次同步的 snapshot 作为恢复源——设备上线时报告自己持有的 reported，影子服务重建
- 最坏情况：desired 丢失 → 设备按自己最后的 reported 继续运行 → APP 端显示"设备状态未知"，等待设备重新上报

**版本号溢出**：version 用 int（最大 21 亿），高频上报设备秒级上报，不停歇大概 68 年才会溢出。实际可以用 bigint，或者在影子重建时重置版本号。这纯粹是面试时的边界情况考察，实际不会触发。

**影子膨胀**：设备功能越来越多，影子 JSON 从 200 字节膨胀到 10KB → 影响 Redis 带宽和同步效率。对策是按模块拆影子——核心状态（电源/温度）走标准影子，非关键状态（固件版本/信号强度）走单独的属性上报通道。

```
┌─────────────────────────────────────────────────────────┐
│                      业务层                              │
│   ┌─────────┐  ┌──────────┐  ┌──────────┐              │
│   │   APP   │  │ 规则引擎  │  │ 管理后台  │              │

│        └────────────┼─────────────┘                     │
│                     │ 更新 desired                      │
│                     ▼                                   │
│  ┌──────────────────────────────────────┐              │
│  │           影子服务 (Shadow Service)   │              │
│  │  ┌────────────┐  ┌────────────────┐  │              │
│  │  │ CAS 更新    │  │ Delta 计算     │  │              │
│  │  │ 并发控制   │  │ 版本管理       │  │              │
│  │  └────────────┘  └────────────────┘  │              │
│  └──────┬───────────────┬───────────────┘              │
│         │ 读写影子      │ 下发指令                      │
│         ▼               ▼                              │
│  ┌──────────┐   ┌──────────────┐                       │
│  │  Redis   │   │ MQTT Broker  │                       │
│  │ (主存储) │   │ (指令通道)   │                       │
│  └────┬─────┘   └──────┬───────┘                       │
│       │ 异步持久化      │                               │
│       ▼                ▼                               │
│  ┌──────────┐   ┌──────────────┐                       │
│  │  MySQL   │   │    设备       │                       │
│  │ (备份+日志)│  │ 执行 delta   │                       │

│                 └──────────────┘                       │
└─────────────────────────────────────────────────────────┘
```

核心设计原则：
- **影子是状态，不是命令**：desired 描述"应该是什么状态"，不是"做某件事"。幂等性天然成立
- **delta 是差异**：只下发 changed fields，不传全量。弱网友好
- **Redis 主存储 + MySQL 兜底**：Redis 扛高频读写，MySQL 做持久化和审计
- **CAS 不用锁**：version 乐观锁足够应对影子更新的并发模式
- **设备上线即同步**：影子机制不依赖实时连接，离线指令不丢失，上线自动补差

---

设备影子本质上是一个**带版本的、双向同步的、最终一致的 JSON 文档**。它的设计哲学是"告诉设备你最终应该是什么样子，而不是每步该做什么"——这恰恰是声明式优于命令式在物联网领域的最佳实践。
