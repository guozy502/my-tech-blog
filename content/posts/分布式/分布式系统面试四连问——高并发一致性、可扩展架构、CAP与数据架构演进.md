# 分布式系统面试四连问——高并发一致性、可扩展架构、CAP 与数据架构演进

> 这四个问题是分布式系统面试的"终极四连问"——从具体的高并发一致性方案，逐层推到 CAP 理论约束，再落到可扩展的架构设计，最后纵观数据架构的十年演进。本文把四问串成一条完整的知识链路。

---

## 一、高并发下如何保证数据一致性

这个问题考察的不是某个单一方案的记忆，而是你能从单机到分布式分层递进地给出答案。五层递进：数据库内置机制 → 缓存双写 → 消息驱动最终一致 → 分布式锁 → 分布式事务。

### 1.1 数据库内置机制：乐观锁与悲观锁

**乐观锁**假设冲突不常发生，提交时才检测；**悲观锁**假设冲突一定会发生，先锁住再操作。

```sql
-- 乐观锁：CAS 更新
UPDATE inventory SET stock = stock - 1, version = version + 1
WHERE product_id = 100 AND version = 5;
-- affected_rows = 0 → 并发冲突，重试或返回失败

-- 悲观锁：行锁
SELECT stock FROM inventory WHERE product_id = 100 FOR UPDATE;
-- 持有锁期间，其他事务的同一行操作阻塞
```

**面试追问：用 version 字段还是用旧值本身做 CAS？**
- version 字段语义清晰，额外维护成本低，是标准做法
- 用旧值 (`WHERE stock = 10`) 在 ABA 场景下不够鲁棒——库存从 10 → 8 → 10，以为没变实则变了

**乐观锁的致命陷阱——重试风暴**：高并发下大量冲突 → 全部重试 → 数据库压力更大 → 冲突更多 → 恶性循环。解法是**随机退避重试**（sleep random 1-50ms）+ **重试次数上限**（3 次后直接返回错误，保护数据库）。

### 1.2 MVCC：读不阻塞写的秘密

MySQL InnoDB 的 MVCC 是面试考察"能否把概念落到源码级别"的分水岭。它不是一个独立的功能模块，而是由**四个东西共同协作**完成的：隐藏列（`DB_TRX_ID` / `DB_ROLL_PTR`）、Undo Log 版本链、ReadView 可见性判断、快照读与当前读的双轨机制。

#### 四个核心组件

**① 三个隐藏列——每行数据自带"时间旅行"能力**

InnoDB 在聚簇索引的每行数据中嵌入了三个隐藏列（你 `SELECT *` 看不到它们，但它们物理存在于页上）：

| 隐藏列 | 大小 | 作用 |
|--------|------|------|
| `DB_TRX_ID` | 6 字节 | 最后一次修改这行的事务 ID |
| `DB_ROLL_PTR` | 7 字节 | 回滚指针——指向 Undo Log 中这行数据的"上一个版本" |
| `DB_ROW_ID` | 6 字节 | 如果没有显式主键，用作聚簇索引键 |

**② Undo Log 版本链——一条链表串联起所有历史版本**

每次 `UPDATE` 操作会在 Undo Log 中创建一个新版本，`DB_ROLL_PTR` 像链表的 `next` 指针一样串联：

```
当前行（聚簇索引页中）：
  id=1, name='C', DB_TRX_ID=300, DB_ROLL_PTR ──┐
                                                  │
Undo Log 链表：                                    ↓
  版本2: id=1, name='B', DB_TRX_ID=200, DB_ROLL_PTR ──┐
                                                       │
                                                       ↓
  版本1: id=1, name='A', DB_TRX_ID=100, DB_ROLL_PTR → NULL（链尾）
```

**两种 Undo Log 的差异**：Insert Undo（INSERT 的回滚日志）在事务提交后立即可删除——因为 INSERT 的数据对其他事务本来就不可见，没人需要它的旧版本。Update Undo（UPDATE/DELETE 的回滚日志）必须保留到所有引用它的事务结束——因为其他活跃事务的快照读需要通过它回溯到"修改前"的版本。后台 Purge 线程负责回收不再被需要的 Update Undo。

**③ ReadView——快照读的"时间戳"**

ReadView 是源码中 `read0types.h` 的结构体，包含 4 个核心字段：

```
m_ids:           创建 ReadView 时，系统中所有活跃（未提交）的读写事务 ID 集合
m_low_limit_id:  活跃事务中最小的 ID（m_ids 的最小值）
m_up_limit_id:   系统下一个要分配的事务 ID（= 已分配最大 ID + 1）
m_creator_trx_id:创建这个 ReadView 的事务的 ID
```

ReadView 要回答的根本问题是：**"修改这行的那个事务，在我开始看的时候提交了没有？"**

**④ 可见性判断算法——`changes_visible()` 五步推演**

当快照读需要读取一行数据时，InnoDB 会根据这行数据的 `DB_TRX_ID` 和当前事务的 ReadView 做五步判断：

```
输入：这行数据的 DB_TRX_ID、当前 ReadView

① if (DB_TRX_ID == creator_trx_id):
     → 这行是我自己改的 → 可见 ✓

② if (DB_TRX_ID < m_low_limit_id):
     → 修改这行的事务在 ReadView 创建前已经提交 → 可见 ✓

③ if (DB_TRX_ID >= m_up_limit_id):
     → 修改这行的事务在 ReadView 创建之后才开始 → 不可见 ✗
     → 沿 DB_ROLL_PTR 回溯到上一个版本，重新从 ① 开始判断

④ if (DB_TRX_ID is in m_ids):
     → 修改这行的事务在 ReadView 创建时还未提交 → 不可见 ✗
     → 沿 DB_ROLL_PTR 回溯到上一个版本，重新从 ① 开始判断

⑤ else:
     → DB_TRX_ID 不在活跃列表中，且在上限之下 → 已提交 → 可见 ✓
```

这个算法的本质是指：**沿着 Undo 版本链回溯，直到找到"在我开始看之前就已经提交的那个版本"。**

#### RC 与 RR 的根源差异——一个时间点

RC（Read Committed）和 RR（Repeatable Read）的行为差异**只由一个因素决定**：ReadView 在什么时机创建。

```
RC：每次 SELECT（严格说是每次快照读）都生成新的 ReadView
  → 每次都能看到其他事务最新提交的数据 → 不可重复读
  → 但是"脏读"仍然被阻止（因为不可见规则 ④ 会过滤未提交的事务）

RR：事务中第一次快照读时生成 ReadView，此后整个事务复用
  → 快照读始终看到事务开始那一刻的数据快照 → 可重复读
```

这个差异有一个重要推论：**RR 下长事务的危险性**。一个事务开启后执行了一次 `SELECT`，ReadView 就此固定。如果这个事务接下来不提交，运行了几个小时——过去几个小时的 Undo Log 都不能被 Purge 线程回收（因为 ReadView 的 `m_low_limit_id` 阻止了 Purge），导致 Undo 表空间膨胀。

```sql
-- 快速找出可能造成 Undo 膨胀的长事务
SELECT trx_id, trx_started,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS duration_sec
FROM information_schema.INNODB_TRX
ORDER BY trx_started LIMIT 5;
```

#### 快照读 vs 当前读——两套完全不同的读取路径

很多面试者在解释 RR 时混淆了这两条路径，这是致命的逻辑错误：

| | 快照读（Snapshot Read） | 当前读（Current Read） |
|------|----------------------|-------------------|
| **SQL** | 普通 `SELECT` | `SELECT ... FOR UPDATE` / `UPDATE` / `DELETE` / `INSERT` |
| **机制** | ReadView → 可见性判断 → 可能回溯 Undo 版本链 | 读最新的已提交版本 → 加行锁 |
| **是否加锁** | 不加锁 | 加锁（Record Lock / Next-Key Lock 等） |
| **RR 下能防幻读？** | ✅ MVCC 天然防（ReadView 不变） | ❌ 需要用 Next-Key Lock 额外保护 |
| **RR 下能防不可重复读？** | ✅ ReadView 复用 | ❌ 每次都读最新提交版本 |

**这个区分直接解释了一个经典困惑**：为什么 RR 隔离级别下，普通 `SELECT` 读到的 name 是 'A'，但紧接着 `SELECT ... FOR UPDATE` 读到的却是 'B'？

答案：快照读走 ReadView（事务开始时的快照 = 'A'），当前读走最新提交版本 + 加锁（'B' 是另一个事务提交的，已经生效）。RR 的"可重复读"只对快照读成立，当前读仍然可能看到其他事务的修改。

#### 幻读在 RR 下是"部分解决"

幻读的定义：同一事务内，两次相同条件的查询，结果的**行数**不同（多了或少了行）。

- **快照读场景**：RR 下 MVCC 解决了——ReadView 不变，其他事务新插入的行由于 `DB_TRX_ID >= m_up_limit_id`（规则 ③），对当前快照读不可见 → 没有幻读
- **当前读场景**：RR 下 MVCC **没解决**——`SELECT ... FOR UPDATE` 读最新版本，其他事务插入并提交的新行仍然会被读到 → 有幻读

**InnoDB 的完整方案**是：MVCC 管快照读 + Next-Key Lock 管当前读。Next-Key Lock 在 RR 级别下锁住索引记录及其间隙，阻止其他事务在查询范围内 INSERT 新行——这就是 RR 下"当前读也防幻读"的底层机理。

MVCC 解决读-写并发，行锁解决写-写并发，Next-Key Lock 解决当前读的幻读问题，三者配合才构成 InnoDB 的完整并发控制。

### 1.3 缓存双写一致性

这是高并发下最经典的面试题。标准范式是 **Cache-Aside**：

```
读：查缓存 → 命中返回 → 未命中查 DB → 写缓存 → 返回
写：更新 DB → 删除缓存（不是更新缓存！）
```

**为什么是"删缓存"而不是"更新缓存"？** 并发写缓存会产生覆盖问题：A 更新 DB → B 更新 DB → B 更新缓存 → A 更新缓存（旧值覆盖新值）。删除缓存 + 下次读时重建，虽然有小窗口不一致，但最终必然正确。

**先删缓存还是先更新 DB？**

```
方案 A（先删缓存）：
  A 删缓存 → B 读发现缺失 → B 查 DB(旧值) → B 写缓存(旧值) → A 更新 DB(新值)
  → 缓存旧值，DB 新值，不一致，且旧值会一直持续到下次缓存失效

方案 B（先更 DB，标准做法）：
  A 查 DB → B 更新 DB → B 删缓存 → A 写缓存(旧值)
  → 理论上存在但概率极低，需要读在缓存失效窗口 + 写在读查完DB后、写缓存前完成
```

**延迟双删兜底**：先删缓存 → 更新 DB → sleep 300ms → 再删一次。用第二次删除覆盖方案 A 的极端窗口。代价是 300ms 窗口内缓存不可用。

**Canal 监听 binlog** 是更彻底的解耦方案，也是阿里等大厂的实际做法：DB 更新 → binlog → Canal 解析 → 发 MQ → 缓存服务消费并删除/更新缓存。异步化彻底规避了应用层的时序竞争，代价是增加了链路延迟和运维复杂度。

### 1.4 消息驱动的最终一致性

当操作跨多个服务时，本地事务搞不定——需要"最终一致性"。

**Outbox 模式**的核心思想：利用数据库的事务保证"业务成功 = 消息一定发出"。

```
BEGIN TRANSACTION;
  INSERT INTO order (...) VALUES (...);        -- 业务操作
  INSERT INTO outbox (event_type, payload) VALUES ('order_created', '{...}');
COMMIT;
-- 事务提交后，异步任务轮询 outbox 表 → 发 MQ → 标记已发送
```

投递方式有两种：定时任务轮询（简单但有时延），或 Debezium 监听 binlog（实时但运维复杂）。消费方通过**唯一键**做幂等：用 `event_id` 或 `业务ID + 操作类型` 去重。

**RocketMQ 事务消息**的原理面试高频：

```
1. Producer 发送 half 消息（对 Consumer 不可见）
2. 执行本地事务
3. 本地事务成功 → commit，Consumer 可见
   本地事务失败 → rollback，消息丢弃
4. 若 Producer 未回传 commit/rollback → Broker 定时回查本地事务状态
```

### 1.5 分布式锁

**Redisson 核心实现细节**：

```lua
-- 加锁 Lua 脚本（原子执行）
if (redis.call('exists', KEYS[1]) == 0) then
    redis.call('hincrby', KEYS[1], ARGV[2], 1);
    redis.call('pexpire', KEYS[1], ARGV[1]);
    return nil;
end;
-- Hash 结构 key: 锁名, field: 线程标识(UUID+线程ID), value: 重入次数

-- 解锁 Lua 脚本（原子执行）
if (redis.call('hexists', KEYS[1], ARGV[3]) == 0) then return nil; end;
local counter = redis.call('hincrby', KEYS[1], ARGV[3], -1);
if (counter > 0) then
    redis.call('pexpire', KEYS[1], ARGV[2]);
    return 0;
else
    redis.call('del', KEYS[1]);
    return 1;
end;
```

三个关键设计点：

- **random_value 校验**：解锁前检查锁是否还是自己持有，防止 A 的锁被 B 误删
- **过期时间**：给锁一个 TTL，防止进程宕机导致永久死锁。过期时间至少是业务执行时间的 2 倍
- **看门狗 (Watch Dog)**：加锁成功后启动后台续期任务，默认每 10 秒续期 30 秒。业务执行完毕取消续期。避免"业务没跑完锁过期了"的问题

**RedLock 的争论**：Martin Kleppmann 批评 RedLock 依赖时间假设，时钟跳跃可能导致安全性失效，建议用 fencing token。业界实际做法：Redisson 单实例在 99% 的场景够用，需要极致可靠性的场景用 ZooKeeper 或 etcd。

## 二、如何设计可扩展的分布式系统

### 2.1 无状态化——分布式第一原则

有状态服务无法直接水平扩展：用户会话绑死在服务器 A，加机器不等于加容量。

```
有状态: 用户 A ←→ 服务器 1 (Session 在内存)
        → 服务器 1 挂了 → 用户 A 的会话丢失

无状态: 用户 A → 任何服务器 → Session 在 Redis
        → 加机器 = 线性加容量
```

实现手段：Session 外置到 Redis、配置外置到配置中心、文件外置到 OSS。登录态用 JWT（客户端携带，服务端只验证签名），但要理解 JWT 的致命缺陷——无法主动失效，必须配合短期 access token (5-15min) + 服务端黑名单。

### 2.2 数据层扩展：分库分表

**分片策略对比**：

| 策略 | 实现 | 优点 | 缺点 |
|------|------|------|------|
| Range (范围) | id 1-1000W → 库0 | 扩容简单，范围查询友好 | 热点不均 |
| Hash (取模) | id % 4 → 库0/1/2/3 | 均匀分布 | 扩容需全量迁移 |
| 一致性 Hash | Hash 环 + 虚拟节点 | 扩容只影响相邻 | 实现复杂 |
| 目录映射 | 查路由表 | 灵活可控 | 路由表本身是瓶颈 |

**分库分表后你失去的能力**：
- 跨分片 JOIN → 要么数据冗余，要么应用层聚合
- 跨分片事务 → 必须用分布式事务或最终一致性
- 全局唯一 ID → 需要雪花算法 (`时间戳 + 机器ID + 序列号`) 或号段模式
- 全局排序/聚合 → 读所有分片 → 内存归并（深分页极慢）
- 随意建索引 → 每个分片独立维护索引，全局修改索引=DDL 在多库重复执行

**分库分表不只是 DBA 的事**——它强制改变了 DAO 层实现、业务代码的数据访问模式、甚至产品功能边界。之前一个 SQL 能解决的"全表搜索"必须走 ES，"总数统计"需要异步计算或接受近似值。理解这种"架构决策向上穿透到产品"的效应，是资深工程师和经验工程师的分水岭。

### 2.3 异步解耦

同步调用链是分布式下最大的不确定性来源：

```
同步: A → B → C → D    (任何一个慢，整条链路阻塞)
异步: A → MQ → B/C/D     (各自独立消费、独立扩容)
```

消息队列的三个核心价值：**削峰**（瞬时流量排队，消费端按自己的节奏处理）、**解耦**（A 不关心 B/C/D 的实现）、**最终一致性**（重试 + 死信保证不丢数据）。

### 2.4 服务治理四件套

规模上来后标配：

- **服务发现**：Nacos/ZK/Consul——新实例上线，调用方自动感知
- **负载均衡**：Ribbon/LoadBalancer——一致性 Hash 用于亲和性路由，加权轮询用于异构集群
- **熔断降级**：Sentinel/Hystrix——下游不可用时快速失败，不拖死上游（线程池隔离 vs 信号量隔离）
- **限流**：令牌桶/漏桶/滑动窗口——保护自己不被打垮。单机限流用 Guava RateLimiter，分布式限流用 Redis + Lua

## 三、CAP 理论——可用性、一致性和分区容忍性的平衡

### 3.1 CAP 的正确打开方式

**最常见的面试错误**："分布式系统只能 C、A、P 三选二。"

**正确理解**：P 不是可选的。网络分区在分布式系统中必然发生，你无法选择"不要 P"。CAP 的真正命题是：**当网络分区发生时（P 已经触发），你选 C 还是 A？**

系统正常运行时 C 和 A 都可以满足——不要把 CAP 理解成"系统设计时永久三选二"。

### 3.2 分区时的两难

```
CP 系统 (分区时牺牲 A，保 C):
  少数派分区拒绝接受写操作 → "我不能保证数据被复制到多数派"
  典型：ZooKeeper 分区期间不可用，等待 leader 选举完成
  场景：银行账户余额、库存扣减、分布式配置

AP 系统 (分区时牺牲 C，保 A):
  两个分区各自接受写操作 → 分区恢复后合并冲突
  典型：Cassandra 所有节点继续可写
  场景：社交媒体点赞数、用户在线状态、商品浏览量
```

### 3.3 PACELC——比 CAP 更实际的模型

CAP 有两个局限：一是不分区时没指导；二是"分区时发生的概率低，大部分时间系统正常运行"。PACELC 补上了这个缺口：

```
P (Partition，分区时):
  选 A (Availability) 或 C (Consistency)

E (Else，正常时):
  选 L (Latency，快返回) 或 C (Consistency，强一致)
```

**工程中更常见的决策其实在 E 这一半**——正常运行时到底要一致性还是要延迟：

- DynamoDB 默认 eventually consistent（选 L），可选 strongly consistent（选 C）但延迟和成本高
- MySQL 主从读写分离：读从库是选 L（可能读到旧数据），读主库是选 C（强一致）
- ZooKeeper 和 etcd 都选 C——即使正常运行时也要保证线性一致性，代价是读性能

**Nacos 的混合设计**值得单独讲：在同一系统中，临时实例走 AP（Distro 协议，高可用）、持久配置走 CP（Raft 协议，强一致）。不搞一刀切，不同数据用不同策略——这是 CAP 在生产中最高级的落地方式。

### 3.4 一致性模型频谱

一致性不是二元开关，而是一个从强到弱的连续谱：

```
强 ───────────────────────────────────────────────→ 弱

线性一致性        顺序一致性       因果一致性        最终一致性
(Linearizability)  (Sequential)    (Causal)          (Eventual)
    │                  │               │                 │
etcd (read leader)  ZK (读follower   向量时钟           Cassandra
所有操作有全局      可能读到旧值)    因果关系正确       "最终"趋于一致
唯一先后顺序                       但并发顺序不定
```

**线性一致性和顺序一致性的关键区别**：线性一致性关心**实时性**——"如果 A 操作在 B 操作开始前就完成了，那么 A 在前 B 在后"；顺序一致性只保证"所有人看到相同的顺序"，不保证这个顺序反映真实时间先后。

**最终一致性的"最终"多久**：没有标准答案。Cassandra 的 QUORUM 读写在毫秒级一致；DNS 缓存变更要等 TTL 过期可能几小时；搜索引擎的索引更新可能到秒级。说"最终一致"时必须明确"多终"——否则就是耍流氓。

### 3.5 典型系统的 CAP 定位与选型参考

| 系统 | CAP 类型 | 一致性的保证手段 | 适合场景 |
|------|---------|----------------|---------|
| etcd | CP | Raft 线性一致读，所有读写走 leader | 分布式配置、服务发现、选主 |
| ZooKeeper | CP | ZAB 协议，leader 选举期间不可用 | 分布式协调（逐步被 etcd 替代）|
| Eureka | AP | 宁可返回已下线实例也不拒绝服务 | 微服务注册中心（可用性优先）|
| Nacos | AP+CP 混合 | AP(Distro) + CP(Raft) 混合架构 | 国内微服务首选注册中心 |
| Redis Cluster | 近似 CP | 异步复制默认 AP，`WAIT` 可配置同步 | 缓存；做分布式锁时需评估风险 |
| Cassandra | AP (可调) | 可配 QUORUM/ALL 提升一致性 | 跨地域高可用、写多读少 |

## 四、数据系统架构的演进趋势

### 4.1 六阶段演进全景

数据架构的增长不是"某天突然决定的"，而是被**数据量和查询复杂度**一步步逼出来的：

```
阶段 1: 单体 MySQL
  单机 → 容量受限、单点故障
        ↓ 读多写少，读先撑不住

阶段 2: 读写分离
  Master (写) + 多个 Slave (读)
  主从延迟是核心矛盾 → 写后立刻读必须走 Master
        ↓ 单库写瓶颈，单表太大

阶段 3: 垂直分库（按业务域）
  用户库 / 订单库 / 商品库 各自独立
  跨库事务和 JOIN 丢失 → 业务代码变复杂
        ↓ 单表仍过亿

阶段 4: 水平分库分表
  order_db_0, order_db_1...，每个库 N 张表
  全局唯一 ID、跨分片查询、扩容迁移——每个都是硬仗
        ↓ 不同查询需要不同存储引擎

阶段 5: 多模存储 (Polyglot Persistence)
  MySQL (核心事务) + Redis (缓存/计数) + ES (搜索)
  + Mongo (文档) + Kafka (事件流)
  多种存储之间数据同步成为噩梦 → CDC 登场
        ↓ "为什么我要管这么多东西？"

阶段 6: NewSQL / 存算分离 / 流批一体
  TiDB、Aurora、Flink——试图简化分布式复杂性
  各自都有效果，但各自也都有新的代价
```

### 4.2 多模存储的一致性协调

阶段 5 是大多数互联网公司的现状。核心挑战不是某一种存储的使用，而是**多种存储之间数据保持一致**。

以"用户下单"为例，涉及 MySQL（核心事务）、Kafka（订单事件）、Redis（购物车缓存失效）、ES（订单搜索索引）、Mongo（详情快照归档）。

这个链路靠三样东西撑起来：

**CDC (Change Data Capture)**：Debezium 监听 MySQL binlog → 解析变更 → 发 Kafka。各下游系统独立消费、各自同步。完全解耦不侵入业务代码，但对数据库有额外 CPU/IO 开销。

**Outbox 模式**：业务方在同一事务中写 `orders` + `outbox` 表，后台异步投递 MQ。CDC 的替代方案，更灵活但侵入代码。

**幂等消费**：消息可能重复投递。ES 用 `_id` 做 upsert，Mongo 用 `upsert`，Redis 用覆盖写——各自利用自身特性保证最终一致性。

### 4.3 NewSQL 是最终答案吗

TiDB 的卖点是"MySQL 协议兼容 + 自动水平扩展 + Raft 强一致"——听起来完美。但：

- 复杂 OLAP 查询不如 ClickHouse，复杂 OLTP 事务不如单机 MySQL
- 运维复杂度不低：tidb + tikv + pd 三个组件，出了问题排查链路长
- 适用边界：**数据量确实大到单库扛不住**时才值得引入，不是为了"跟上潮流"

面试时要有判断力：**大部分公司的 MySQL 8.0 + Redis + ES 离天花板还远**，先把索引优化、慢 SQL 治理、缓存策略做好的 ROI 远高于上 NewSQL。

### 4.4 值得关注的三个趋势

**存算分离**：AWS Aurora / 阿里云 PolarDB 将计算（SQL 引擎）和存储（分布式存储层）解耦。核心创新是只把 redo log 下推到存储层——不是传整个 data page，网络传输量降低一个数量级。计算节点可以秒级弹扩/弹缩，存储自动伸缩。

**Data Lakehouse**：Iceberg / Hudi / Delta Lake 让数据湖（S3 存原始数据）有了 ACID 事务、Schema 演进和 Time Travel。数据湖"和"数据仓库"的边界在模糊——本质是"存储和查询引擎解耦"，同一份数据被 Presto/Trino/Flink/Spark 各自查询。

**流批一体**：经典 Lambda 架构（实时链路 + 批处理链路）的终结。Flink 支持同一套代码既做流处理也做批处理——Kappa 架构主张只保留流处理，批处理本质就是"回放历史流数据"。

### 4.5 整个演进史的核心矛盾

```
数据量增长 → 单机扛不住 → 分片（失去事务/JOIN）
                            ↓
                  引入多模存储（失去一致性）
                            ↓
                  CDC/消息/最终一致性（增加复杂度）
                            ↓
        NewSQL/云原生 试图把分布式对业务透明化
        但引入新的性能损耗和运维负担
```

**扩展性、一致性、开发效率**——三样东西你最多同时要两样。

## 五、四问之间的内在关联

把四问放回一起看，它们不是孤立的面试题，而是一条完整的知识链：

```
高并发数据一致性 ──→ 具体方案怎么选？
      │
      │  乐观锁/悲观锁 (单机兜底)
      │  Cache-Aside (缓存双写)
      │  分布式锁 (Redis/ZK)
      │  最终一致性 (MQ/CDC/Outbox)
      │  分布式事务 (2PC/TCC/Saga，本文未展开)
      │
      ▼
CAP 理论约束 ────→ 你选的每个方案，都必然在 C 和 A 之间做了取舍
      │           Cache-Aside 选 A（短暂不一致比服务不可用强）
      │           分布式锁选 C（锁不一致就是灾难）
      │
      ▼
可扩展架构设计 ──→ 所有扩展性决策都会引入新的一致性问题
      │           分库分表 → 跨分片不一致怎么办
      │           异步解耦 → 最终一致性窗口多大
      │           读写分离 → 主从延迟容忍多少
      │           多模存储 → 多种存储数据怎么对齐
      │
      ▼
数据架构演进 ────→ 过去十年，整个行业就是在
                  扩展性 ↔ 一致性 ↔ 复杂度 之间反复找更优平衡点
```

**一条线索串到底**：高并发一致性是"要解决的问题"，CAP 是"不可逾越的理论约束"，可扩展设计是"现实工程手段"，架构演进是"整个行业在这条路上的十年探索"。
